# 《数据库应用实践》课程报告

## 高校就业与招聘管理模块

版本：1.0。项目：AI Interview 网站的就业管理模块。报告日期：2026 年 10 月 13 日。

界面分为教师端和学生端：教师集中查看全体学生档案、简历投递、附件及面试录用；学生仅查看本人的资料和进度。数据库 15 张业务表和 99 个字段具有中文 COMMENT，含关系、单位、状态与 UTC 时间说明。V3 在既有结构上增加注释和档案完整性检查，不修改已应用的 V1/V2。

案例性质：高校就业服务中心的教学案例。企业、学生与招聘信息均明确标注为课程演示，不代表真实机构调研和真实就业结果。团队成员与教师信息由实际提交者据实填写。

## 第一章 系统规划

原项目具备登录、简历管理、模拟面试、社区、简历市场及知识库功能，但主要围绕 AI 工具展开。课程指导书要求展示需求分析、概念与逻辑设计、基础数据维护、主从业务处理、查询统计、完整性约束和权限管理。就业管理模块以投递、面试和录用为主线，把数据库设计与实际业务连接起来。

界面分为教师端和学生端。教师与管理员进入教师端，集中查看全体学生档案、简历投递、面试与录用；学生端仅展示本人资料和求职进度，不提供教师端的管理页面。系统授权角色仍为学生、教师和管理员。学生查找岗位并跟踪个人进度，教师维护招聘资料、审核、评分和登记录用，管理员分配模块身份和权限。企业是被管理的基础资料，不提供企业独立登录。

项目采用同一前端网站和独立后端服务。网站仍使用 18181 端口；模块后端使用 18184，MySQL 使用 13308。就业业务数据存储在 employment_course 中；原站身份认证和旧业务仍使用 PostgreSQL。不能将整个网站描述为只有一个 MySQL 数据库。

为配合 IDEA 查看和 SQL 课程实验，已在用户原有的本机 MySQL 8.0.42（3306）建立同名独立副本。副本包含业务表、中文字段注释、三个可查询视图、四条迁移记录和完整样例数据。网站仍以 Docker 中 13308 的库为运行数据源，两个库不自动同步；本机 SQL 练习不会改变网站的业务事实，也不覆盖其他课程数据库。

技术平台为 React、TypeScript、Java 21、Spring Boot 4.0.1、MySQL 8.4、Flyway、JPA 与 JDBC，以及 Docker。模块不包含 Spring AI 或 pgvector 依赖。附件使用现有 MinIO 的独立私有桶。成本为现有电脑、开源软件和实际投入时间，不编造经费。

实施分三个阶段：第一阶段完成基础结构、身份和资料维护；第二阶段完成投递、评分、录用和报表；第三阶段进行约束、并发、恢复、浏览器验证并整理材料。报告中的测试由自动化脚本实际执行，人工访谈和团队分工不能以自动化结果代替。

## 第二章 需求分析

组织职能为：管理员负责授权与访问控制，就业中心教师负责业务维护，学生负责个人档案与求职申请。全局管理员身份来自原站；教师身份仅在就业模块生效。模块停用普通账户不会影响其使用社区等旧功能。

学生需要填写学号、姓名、学院、专业、毕业年份，完成档案后投递开放岗位。投递必须满足岗位未截止、企业启用和名额未满。同一学生对同一岗位只允许一条申请。简历附件可选，上传失败不阻断不带附件的投递。

教师需要维护企业和岗位，对新申请开始审核、拒绝申请或安排多轮面试。每轮面试记录时间、地点、面试官和三个评分项目。最终录用必须建立在至少一次已完成面试上，且不能超出岗位名额。

查询需求包括姓名、学号、企业、岗位等关键词查询，状态筛选、学院与毕业年份筛选、分页和白名单排序。输出需求包括岗位招聘汇总、学生就业明细、按投递时间选择批次的处理统计，以及 CSV 和浏览器打印 PDF。

边界：三天版本不包含企业门户、视频面试、AI 评分、通知系统、撤销最终录用及已完成评分修改。原有社区、简历市场和 AI 功能沿用旧接口。两个 Word 模板继续下载原始文件。

## 第三章 概念结构设计

核心实体为账户映射、角色、权限、菜单、学生、企业、岗位、简历附件、投递、面试轮次、评分项目、评分明细、录用结果和操作日志。全局 ER 图源代码见 er-diagrams.md；数据库关系在下述业务分图和授权分图中展开。

关系设计：企业与岗位一对多；学生与岗位通过投递形成多对多；投递与面试轮次一对多；面试轮次与评分明细一对多；评分项目与评分明细一对多；学生与最终录用结果一对零或一；角色和权限通过关联表形成多对多。

账户映射只保存原站用户编号和模块状态，不复制密码。账户与学生档案一对一。简历文件属于一个账户，可被本人的投递引用。操作日志关联操作者，保存业务对象编号、动作、时间和摘要，不记录 Token 或密码。

业务流程图：学生档案完成后选择岗位，创建投递；教师审核并安排面试，提交评分后登记录用；数据进入视图和报表。数据流包括学生输入、原站认证结果、招聘资料、评分表、录用登记和查询条件，各项输入经权限与业务校验后写入对应表。

## 第四章 逻辑结构设计

数据库包含 15 张业务表和 3 个业务视图，Flyway 另有迁移历史表。该数量是实现选择，不是指导书规定的最低要求。

| 分组 | 表 | 数据作用 |
| --- | --- | --- |
| 授权 | users、roles、permissions | 原站账户映射、模块角色和可执行操作 |
| 授权 | role_permissions、menus | 角色权限关系与动态导航 |
| 资料 | students、companies、jobs | 学生档案、企业与招聘岗位 |
| 业务 | applications、interview_rounds | 投递主记录和面试轮次明细 |
| 评价 | evaluation_criteria、interview_scores | 固定评分标准与逐项得分 |
| 结果 | employment_results | 每名学生的最终录用登记 |
| 资源 | resume_files、audit_logs | 附件元数据和操作追踪 |

各表使用 BIGINT 主键。业务唯一性通过学号、外部账户编号、企业代码、学生与岗位组合、投递与轮次组合、面试与项目组合表达。关联字段使用外键，避免没有学生的投递、没有面试的评分和错误录用关联。

评分明细和面试轮次拆表，避免把多轮评价全部放进 JSON。岗位招聘名额和已录用人数是明确的数值字段；原子更新与录用结果共同维护计数，验收查询核对两者一致。

视图 v_application_detail 每条投递一行，关联学生、岗位、企业和最新一轮面试。v_job_recruitment_summary 每岗位一行，面试人数按不同投递计数。v_student_hiring_summary 每学生一行，关联其申请总数和最终录用。子表先汇总后连接，防止一对多连接放大统计。

权限矩阵：学生仅操作本人档案、投递、面试结果和附件；教师按被授予的资料维护、审核、评分、录用及报表权限操作；管理员维护模块授权。管理员权限固定保留，学生和教师不能被授予越界的管理员权限。

## 第五章 物理设计

MySQL 使用 InnoDB 和 utf8mb4。初始结构、固定权限、菜单、评分项目和视图由版本化 SQL 创建。JPA 只执行 validate，验证实体与数据库类型的一致性；复杂关联查询和业务写入使用 JDBC，事务由 Spring 管理。

索引覆盖开放岗位与截止时间、企业关联、投递状态、投递日期、面试时间、毕业年份和学院、日志时间及业务对象。唯一索引同时用于完整性约束和关联查询。字段级字典与索引、外键、CHECK 定义见 data-dictionary.md 和实际迁移 SQL。

关键 CHECK：招聘名额为正，已录用人数在零与招聘名额之间；得分在零与项目上限之间；毕业年份为 2000 至 2100；投递、岗位、档案和面试状态限制在已定义集合中。录用结果的申请编号与学生编号通过组合外键一致绑定。

评分事务锁定相关学生、投递和面试，插入三个项目的得分，由后端相加得到总分，并更新完成状态和日志。出现任何数据库错误，全部回滚。录用事务锁定学生和申请，用条件 UPDATE 增加名额，只有更新成功才插入最终录用和日志。名额满时不产生半条录用记录。

| 功能 | 输入 | 处理 | 输出 |
| --- | --- | --- | --- |
| 档案维护 | 学号、姓名、学院等 | 格式校验、唯一检查、保存 | 已完善档案 |
| 岗位投递 | 岗位、可选附件、说明 | 所有权、状态、时间、名额校验 | 投递记录 |
| 面试评分 | 三项得分、评价 | 检查上限、事务写明细、计算总分 | 已完成面试 |
| 录用登记 | 申请、入职日期、备注 | 状态检查、原子名额更新、写入结果 | 最终录用 |
| 查询报表 | 条件、分页和排序 | 视图查询、去重统计、格式化 | 页面、CSV、打印 |

时间存储采用 UTC，界面和日期筛选采用北京时间。日期批次以投递时间为准，结束时间采用不包含上界的查询方式，页面把选定结束日期换算为次日零点。

## 第六章 系统实施

前端在原站路由中增加 /employment 和模块内导航；原有悬浮导航新增就业管理。企业、岗位、投递、评分、录用、报表、权限通过独立后端 API 实现。模块代理按 /api/course/ 转发，其他 API 继续转发原后端。

身份核验由就业后端携带原 Token 调用原站 /api/auth/me，检查业务码与用户数据。原站返回 HTTP 200 不代表业务成功。认证超时返回暂不可用，而非错误清除用户登录。模块不解码未经核验的用户资料，也不复制原站签名密钥。

账户映射在首次访问或管理员分配身份时建立。教师身份保存在 MySQL，原站角色仍为普通用户。管理员用户列表读取原站目录并合并模块角色。原站增加只读用户详情接口以核对目标用户，不返回密码哈希。

附件只接收实际 PDF 或 DOCX 内容，最多 10MB。DOCX 检查文档结构和解压体积，不提取归档路径。文件写入独立私有桶，MySQL 保存对象键、所有者、文件名、大小和类型。通过模块接口授权下载，匿名对象访问被拒绝。

显式演示脚本生成 10 家企业、20 个岗位、30 名学生、60 条投递、36 轮面试和 12 条录用。名称、说明和评价均标注为虚构课程演示。验收脚本另外产生名称带验收标识的数据，不应把它们计入上述演示清单。演示密码随机生成，只保存在本机忽略版本控制的目录中。

部署脚本先编译当前源码，再生成 Docker 运行镜像。该方式避开本次 Docker Hub 构建镜像下载失败的问题；标准多阶段 Dockerfile 仍保留。MySQL 使用独立数据卷，原站镜像与数据库有备份。部署脚本不会删除旧数据卷。

## 第七章 系统测试

测试分为内容校验单元测试、实际 MySQL 和 HTTP 接口验收、真实 Chrome 浏览器验收，以及备份恢复、停机隔离和持久化验证。执行日期、用例、证据及问题记录由自动化输出生成，汇总见 test-results.md。测试人员记为 Codex 自动验收；人工审核人员由实际组员填写。

评分回滚测试使用仅针对测试面试编号的临时触发器，使第三条评分违反 CHECK，验证前两条评分也被回滚，并在 finally 中移除触发器。并发测试以两个不同学生同时竞争同一岗位最后一个名额，核对成功与拒绝次数、计数和录用表。

权限测试覆盖未登录、失效 Token、普通用户访问管理员接口、跨学生撤回和评分读取、模块停用、教师与原站身份隔离、动态菜单和后台权限同步变化。下载测试比较两个原 Word 文件的 SHA-256，确认不是占位接口。

浏览器覆盖 2530、1440、1250、1100、1024、840、800、768、740、390、320 像素宽度，检查页面横向溢出、顶部焦点边框、表格容器和模态框。真实截图和打印样例保留在本机验收目录。

性能测试在独立临时数据库建立 1000 名虚构学生、1000 条投递和 2000 轮面试，执行 EXPLAIN ANALYZE 后删除临时数据库。CLI 往返耗时包含 Docker 执行开销，不能冒充纯 SQL 延迟。各条服务器执行计划另行保存，作为索引和连接方式的分析依据。

实测发现与处理：布尔实体最初使用了不匹配的 JDBC 类型，改为 Boolean 后通过 JPA 校验；MySQL CHECK 异常被通用处理器归为 500，补充错误码 3819 识别后正确提示约束冲突；恢复测试初次命中初始化服务器，改为等待 TCP 服务；部分正常 Word 归档不兼容流式 ZIP 读取，改用中央目录校验并增加原文件回归测试。字段 COMMENT 迁移最初误用等号语法，在独立库修正验证，仅清除失败的 V3 标记后重放，成功迁移历史和业务数据保留。

## 第八章 用户操作手册

学生：使用原站账户登录，点击就业管理；在我的档案完善信息；打开招聘岗位，查看要求并投递。可先在我的投递上传附件，再在投递表单中选择文件。我的投递可以查看状态和撤回未终结申请；我的面试查看轮次、评分和评价；我的录用查看最终结果。

教师：由管理员在模块管理中分配身份，重新打开模块后进入企业管理和招聘岗位；在投递审核中开始审核，再安排面试；面试管理中填写三项得分，确认前检查，因为完成后不能重评；在投递或录用登记中确认最终录用。岗位招聘名额不能低于已录用人数。

管理员：直接复用原站管理员身份。在模块管理查找原站用户，设置 USER 或 STAFF，以及模块启用状态。角色权限区只允许修改该角色业务边界内的权限，工作台权限必须保留。操作记录用于追踪授予身份、评分、录用和其他变更。

报表：选择岗位汇总、学生明细或投递批次统计，设置筛选后查询；导出全部结果生成 UTF-8 CSV，单次最多 10000 条；打印当前页按 A4 横向布局保存 PDF。系统登记录用比例以已完善且启用的学生档案为分母，只代表本系统记录覆盖程度。

## 第九章 开发总结

改造将原本以 AI 工具为中心的网站补充为具备结构化就业业务的系统。课程知识通过表关系、主外键、唯一与检查约束、视图、显式关联查询、事务、并发控制和动态权限得到实际体现。

独立后端减少新业务对旧 PostgreSQL、向量服务和 AI 配置的影响。共享认证避免重复登录，但认证服务不可用时模块受保护请求也不能执行，这是已选择架构的实际依赖。现版本适用于课程演示和小规模管理；没有宣称生产级可用性或真实机构调研完成。

实际改动、测试和成本应结合提交者的工作记录补充。可扩展方向包括最终录用更正审批、评分版本记录、通知、企业门户和合规的数据保留策略。本次不把这些未实现功能写入验收成果。

## 第十章 运行维护

运行时保留原站前端、原后端、PostgreSQL、Redis、MinIO，新增就业后端和 MySQL。健康接口只提供模块状态。观察容器健康、认证连通和数据库连接，避免把 AI 服务错误当作就业业务的必需条件。

MySQL 密码保存在本机 .env，不进入报告和源码。备份使用单事务导出；恢复演练在独立临时 MySQL 容器中进行，不覆盖运行数据库。附件元数据备份不等于文件备份，完整恢复还必须保留或备份 MinIO 数据卷与私有桶内容。

跨服务器复制时，视图定义者调整为目标导入账户，以免 Docker 中的账户在目标服务器不存在。恢复检查同时核对业务表和三个视图，而不是只检查建表是否成功。本机复制脚本仅接受新建空库，拒绝覆盖已有库，并保存源快照与核对记录；目标账户的密码通过进程环境传入，不作为命令行参数或写入版本库。

回退时保留就业 MySQL 数据卷，恢复旧前端和后端镜像并停止就业服务。禁止执行 down -v 或把 MySQL 挂载到旧 PostgreSQL 数据卷。标准启动及本机编译部署命令见 deployment.md。

维护记录应包含日期、现象、检查、原因、处理和复测结果。本次日志如实记录构建镜像下载失败、实体类型修复、约束错误提示修复和 Word 兼容修复。新需求应另行评估数据迁移、权限与事务影响，不直接修改已有迁移历史。
